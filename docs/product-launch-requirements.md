# 车位租售小程序：上线需求与实施基线

> 本文是对 `business-review.md` 的产品、权限与上线补充；它不覆盖或替代其中的微信登录实现说明。目标是把当前“发布/审核信息”的原型收敛为可在**单一社区或单一合作停车场**试运营的 MVP。多社区、在线交易与跨城市场不在首发范围。

## 1. 结论与定位

当前产品适合定义为「社区停车位出租/出售**信息撮合与线下履约**平台」，而不是“停车场管理系统”或“在线交易平台”。首发只服务已签约的一个社区/停车场，由物业或运营方审核供给；平台不收款、不担保产权、不代替合同。

上线前必须先完成 P0。否则任何普通小程序账号有机会调用后台管理接口，且后台前端对成功响应的处理已与后端不一致，不能视为可上线。

## 2. 已审查到的 P0 缺口

| 问题 | 代码证据 | 上线风险 | 必须验收的结果 |
| --- | --- | --- | --- |
| 后台没有角色授权 | `UserSecurityInterceptor` 只校验 `channel=admin`；`/api/admin/**` 无 `role/isAdmin` 校验 | 普通账号登录后台后可管理用户、审核和删除信息 | 管理端接口仅 `ADMIN` 角色可调用；运营审核员使用最小的 `AUDITOR` 权限 |
| 密码明文与固定默认密码 | `UserLoginValidator` 遍历全量用户、明文比较；`UserService` 默认 `123456` | 账号接管、撞库和数据泄露 | 使用 BCrypt/Argon2 哈希；首次登录强制改密；限流、失败锁定和审计日志 |
| 管理端成功码不兼容 | 后端 `ApiResponse` 成功为 `code:200`，`park-admin/services/request.ts` 只接受 `code===0` | 后台登录和 CRUD 会被前端判为失败 | 统一契约为 HTTP 2xx + `success:true` + `code:200`，前后端增加契约测试 |
| 数据库基线不可信 | `database-schema.md` 的 `user` 缺 `openid/channel/role`；`market` 缺 `audit_remark/buildings`，但 Mapper 已使用 | 新环境建库或发布时会失败/丢功能 | 提供版本化迁移脚本（Flyway/Liquibase），CI 从空库执行迁移并验证 |
| 撤回为物理删除 | `MarketService.delete` 删除主记录和图片关系 | 无审计、无法恢复，投诉不能追溯 | 改为软删除/`WITHDRAWN` 状态，保留操作者、时间、原因和历史 |
| 登录态仅在单进程内失效 | `AuthTokenService` 使用内存黑名单 | 重启或多实例后，已登出/被踢 token 可恢复使用 | 生产使用 Redis 或数据库会话/版本号；所有实例共享失效状态 |

同时整改：上传接口限制 MIME 类型、扩展名、大小和图片数量；对象存储私有读/签名 URL；日志中不得出现 token、openid、手机号或密码；移除旧接口兼容层前完成调用方迁移并在网关拒绝旧路径。

## 3. 首发 MVP 需求

### 3.1 角色与边界

| 角色 | 权限 |
| --- | --- |
| 游客 | 浏览已上架车位、搜索和查看详情；不展示完整联系方式 |
| 已验证住户/车位发布者 | 发布、编辑、撤回自己的信息；查看自己的审核状态和拒绝原因 |
| 审核员 | 仅审核所属社区的车位，填写通过/拒绝原因，不管理账号或系统配置 |
| 社区管理员 | 管理所属社区、审核员和内容；查看运营数据 |
| 平台超级管理员 | 仅用于平台配置与故障处置；高风险操作须审计 |

首发必须引入 `community_id`（或 `parking_lot_id`）作为核心租户边界。所有车位、用户归属、审核员权限、查询条件和审计日志都必须带该字段；服务层强制根据 JWT 中的社区范围过滤，不能相信客户端传入的 `userId` 或社区 ID。

住户验证采用物业导入/邀请码/人工核验三选一，首发推荐“物业白名单 + 人工审核”。未验证用户可浏览，不能发布。不要用手机号或 GPS 作为住户身份凭证。

### 3.2 状态机与业务规则

车位状态固定为：`DRAFT → PENDING → PUBLISHED → OFFLINE`，以及 `PENDING → REJECTED → DRAFT`、任意可见状态 `→ WITHDRAWN`、管理员 `→ CLOSED`。

- 新发布或修改已发布内容后进入 `PENDING`；审核通过后才 `PUBLISHED`。
- `REJECTED` 必须有面向用户的拒绝原因；`CLOSED` 必须有后台处置原因。
- 发布者只能编辑本人且处于 `DRAFT/REJECTED/PENDING` 的记录；已发布内容变更须重新审核。
- 列表和详情只展示本社区的 `PUBLISHED` 记录；发布者可查看自己的全部状态。
- “出租”和“出售”必须分别录入计价单位、最短租期/可租日期，出售还需声明产权/使用权信息仅由线下核验。
- 联系方式默认掩码；点击“联系发布者”须二次确认并记录联系事件。首发推荐平台客服/订阅消息转达，不直接暴露手机号。
- 禁止发布虚假、重复、歧视、引流、违法交易信息；设置举报入口和 24 小时内处置 SLA。

### 3.3 首发页面与闭环

1. 首页：当前社区、出租/出售筛选、车位编号/楼栋筛选、仅显示已上架内容。
2. 详情：图片、位置描述、价格与单位、可租日期/租期、规则、联系方式掩码、举报。
3. 发布：社区归属不可手填；字段校验、图片上传、保存草稿、提交审核。
4. 我的发布：状态、审核原因、编辑、撤回、重新提交。
5. 消息：审核通过、拒绝、下架、举报处理结果；订阅消息必须由用户主动授权。
6. 管理端：待审队列、审核详情、批量下架、举报处理、用户/社区权限、操作日志与基础报表。

首发不做：平台担保交易、在线支付/退款、车牌识别、自动闸机、车位实时占用、跨社区搜索、地图精准定位、推荐算法。要做这些必须另立需求、资金与合规评审。

## 4. 必备数据与接口契约

新增或迁移的数据至少包括：

- `community`、`user_community_role`：社区及用户角色范围。
- `market`: `community_id`、`status`、`audit_remark`、`audited_by`、`audited_at`、`withdrawn_at`、`closed_at`、`version`。
- `market_audit_log`：状态前后值、原因、操作者、时间、请求追踪 ID。
- `report`：举报对象、类型、说明、状态、处理人和处理结果。
- `operation_log`：登录、审核、下架、导出、权限变更、强制下线等高风险行为。
- `login_attempt`/共享会话存储：登录失败限流和会话失效。

所有写接口须：服务端取当前用户和社区、请求幂等键、参数白名单 DTO、乐观锁 `version`、统一错误码（`401` 未认证、`403` 无权限、`409` 状态/版本冲突、`422` 参数不合法）。禁止把 JPA/MyBatis 的 `User`、`Market` 实体直接作为小程序请求/响应对象。

接口迁移完成条件：`/api/wechat/**` 和 `/api/admin/**` 是唯一公开业务前缀；旧路径先返回弃用响应并监控 30 天无调用，再删除。后台端的 `/api/admin/**` 还必须通过 RBAC 校验，不能仅依赖 JWT 的 channel。

## 5. 非功能与上线门槛

- 安全：HTTPS、密钥仅由部署环境注入；密码哈希；生产 JWT 密钥校验；共享 token 失效；接口限流；依赖漏洞扫描；文件安全校验；备份和恢复演练。
- 隐私：最小化采集；手机号、位置、相册/相机、openid 的用途、范围、保存期限和删除路径写入隐私政策；权限仅在用户触发功能时申请。用户可注销账号、导出/删除其可删除的数据并获知处理结果。
- 稳定性：健康检查、结构化日志、告警、异常追踪、每日数据库备份、对象存储生命周期、测试/预发/生产隔离；不得在生产 Swagger、客户端或日志中暴露密钥。
- 质量：后端单元+集成测试覆盖认证、RBAC、状态机、归属校验、并发审核和上传；前端覆盖登录、发布、审核、撤回、401、网络失败；做真实小程序设备回归。
- 可观测性：为每个请求生成 trace ID，仪表盘至少含登录成功率、审核时长、发布转化、举报率、错误率和接口 P95。

## 6. 分期与验收

### P0：安全可用（上线前，阻塞发布）

完成第 2 节全部事项、社区隔离、状态机、软删除与审计；修正管理端响应处理；补数据库迁移；补隐私政策、用户协议、举报与客服入口；完成冒烟/回归/备份恢复演练。验收：普通用户无法访问任一 admin 接口；审核员不能越社区审核；重启和双实例后已撤销 token 均无效；每次状态变化可追溯；从空库可以部署成功。

### P1：试运营（1 个社区）

住户验证、消息通知、审核队列、报表、举报处置、内容审核规则、客服 SOP。验收：从注册到发布、审核、联系、撤回、举报可闭环，运营可在后台定位任一记录和处理责任人。

### P2：增长验证（连续 4 周试运营后）

邀请机制、楼栋/车库精细筛选、运营活动、数据漏斗、商家/物业多租户能力。只有供给量、联系转化和投诉率达到预设目标才扩大社区。

## 7. 推广与运营建议

首发不要投放泛流量。以合作物业为渠道：在车库入口、业主群、物业公众号和入住流程中展示二维码；物业审核员承诺 24 小时审核；首批发布者免审核排队或提供停车券/物业积分（须由物业承担和确认规则）。

每周只追踪五个指标：已验证住户数、有效上架量、浏览到联系转化、审核中位时长、举报/投诉率。建议首发门槛为“至少 30 条真实供给、审核中位时长小于 24 小时、连续两周投诉率低于 1%”，达到后再复制到第二个社区。

交易仍在线下完成时，页面必须明确“平台仅提供信息服务，价格、产权/使用权、履约由双方线下核验与协商”。若未来接入支付、定金、经纪撮合或产权证明核验，先进行法律、支付资质、资金存管和平台规则专项评审。

## 8. 小程序发布合规清单

- 在微信公众平台选择与实际服务一致的类目、提交可复现的审核账号/路径和完整功能页；不得以审核后隐藏或改变服务内容规避审核。
- 完成 APP/小程序备案、域名 ICP 与 HTTPS 配置后再发布；境内提供互联网信息服务的小程序应依法履行备案手续。
- 配置并逐项核对隐私保护指引：本项目现有 `wx.getLocation`、相册/图片上传、联系方式、openid 与可能的订阅消息均须按真实用途声明；不得因用户拒绝非必要权限而拒绝浏览基本服务。
- 上线前准备：用户协议、隐私政策、内容规范、投诉处理和联系方式、账号注销/数据删除流程、审核与封禁 SOP。

依据：工信部《[关于开展移动互联网应用程序备案工作的通知](https://www.gov.cn/zhengce/zhengceku/202308/content_6897341.htm?type=mobile-internet)》明确小程序属于备案范围；《[常见类型移动互联网应用程序必要个人信息范围规定](https://www.miit.gov.cn/jgsj/xgj/gzdt/art/2021/art_4e535277ab4343ee9010dbbaf90aab64.html)》适用于小程序并要求最小必要；腾讯云 2025 年的《[小程序隐私保护指引适配说明](https://cloud.tencent.cn/document/product/1301/97930)》说明隐私接口/组件须在指引中声明并取得相应同意。具体类目、备案和审核材料以提交当日微信公众平台规则为准。

## 9. 给 OpenCode 的实施顺序

1. 不改变业务功能前提下，先写安全与契约回归测试，复现 P0 问题。
2. 引入密码哈希、RBAC、共享会话失效、请求 DTO/VO 和统一响应契约；删除敏感日志。
3. 建立数据库迁移，导入现有数据并添加社区、状态机、审计与软删除字段/表。
4. 在 Service 层实现社区范围、归属、状态流转和乐观锁；Controller 只接收 DTO。
5. 对齐管理端和小程序 API，完成端到端回归；旧接口加弃用监控，不能提前删除。
6. 补运维配置、健康检查、备份恢复、监控与发布流水线；预发演练通过后才提审。

任何 P0 未通过时，禁止将版本标记为生产可用。
